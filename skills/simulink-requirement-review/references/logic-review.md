# 功能逻辑审查

## 1. 需求 → 子系统映射

按需求文档的功能描述定位实现位置（子系统名/模块名）；spec JSON 的 `subsystems` 可直接映射。无法映射的“需求功能”或“模型逻辑”都要记录（需求未实现 / 模型多余功能）。

## 2. 核对逻辑语义（用 model_read 的表达式）

- **比较方向**：`>=` 与 `>`、`<=` 与 `<` 是否与需求一致（“达到即触发”还是“超过才触发”）；
- **滞环/死区**：上/下阈值 = 中心 ± 半宽 是否正确；
- **计数/防抖/超时**：周期数阈值与采样周期换算（N 周期 = N × Ts）；计数器清零/保持时机；
- **门控/仲裁**：使能条件、优先级（如 Operating>Failed>HbLost）、合并/选择逻辑；
- **标定量**：cal_* 数值/类型/单位与需求一致（用 `model_resolve_params` 确认实际值）；
- **状态机**：转移条件、优先级（ExecutionOrder）、默认转移、可达性（`stateflow_lint`）；嵌套状态与需求是否一致。

## 3. 佐证验证（可选，不改模型）

- 对关键场景用 `sim`（SimulationInput + Dataset）或 `model_test` 快速验证输出是否符合需求预期；
- 行为偏差作为高严重度证据。

## 4. 严重度

- **高**：功能与需求相悖、阈值/方向错误、端口类型错误；
- **中**：边界/时序/编码细节偏差；
- **低**：命名、描述、风格问题（如 double、门电路形状逻辑块等风格项）。
